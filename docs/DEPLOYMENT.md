# Deployment

Marquee runs on Cloud Run, in one GCP project, in one region, described entirely by
Terraform and deployed by a GitHub push. There is no manual step after the first one.

- **Project**: `quantum-pulsar`
- **Region**: `us-central1`
- **Deploy branch**: `claude/group-event-wallboard-gcp-aqi0q3` (and `main`)

---

## Why this shape

| Piece    | Choice                       | Why                                                                                                           |
| -------- | ---------------------------- | ------------------------------------------------------------------------------------------------------------- |
| Compute  | Cloud Run, min-instances 0   | Traffic is event-shaped: nothing for a week, then a party. Scale-to-zero costs nothing between them.          |
| Database | Firestore, regional          | Real-time listeners are what make the wall live. Regional is ~⅕ the per-operation price of multi-region.      |
| Media    | Cloud Storage, private       | Uploads and downloads go browser↔bucket, so media bytes never pass through billed Cloud Run CPU.              |
| Images   | Artifact Registry            | Same region as the service, so pulls are not cross-region egress.                                             |
| Secrets  | Secret Manager               | Generated by Terraform, read at start-up. Never a build argument, never in an image layer, never in the repo. |
| Expiry   | Firestore TTL + Scheduler    | TTL deletes documents for free; the hourly sweep deletes the bytes, which is what expiry actually means.      |
| CI → GCP | Workload Identity Federation | No service-account key exists to leak, rotate, or forget.                                                     |

### Region

`us-central1`. It is in Cloud Run's cheapest pricing tier, has the lowest Cloud Storage
rate, and supports regional Firestore. Cloud Run, the bucket and the database are all in it
on purpose — reads across regions are billed as network egress, and media is the one thing
this app moves in volume.

**Firestore's location is permanent.** Changing it later means a new database and a
migration, so this is the one decision here that is genuinely hard to reverse.

## First deploy

### 1. Bootstrap, once

From a machine signed in to `gcloud` as an owner of the project:

```bash
gcloud auth login
./infra/bootstrap.sh quantum-pulsar us-central1 teja1989/wallboard
```

It creates only the four things that have to exist before Terraform can run at all — the
APIs Terraform itself calls, a versioned bucket for Terraform state, a Workload Identity
pool that trusts this one repository, and a deploy service account that pool may
impersonate. Terraform owns everything else.

The script is idempotent; running it twice is safe.

It prints the repository variables to set, and the `gh` commands to set them.

### 2. Set the repository variables

Settings → Secrets and variables → Actions → **Variables** (not Secrets — none of these is
secret; the identity provider only mints tokens for this one repository):

| Variable                         | Value                                       |
| -------------------------------- | ------------------------------------------- |
| `GCP_PROJECT_ID`                 | `quantum-pulsar`                            |
| `GCP_REGION`                     | `us-central1`                               |
| `GCP_WORKLOAD_IDENTITY_PROVIDER` | printed by the bootstrap script             |
| `GCP_DEPLOY_SERVICE_ACCOUNT`     | printed by the bootstrap script             |
| `TF_STATE_BUCKET`                | printed by the bootstrap script             |
| `OWNER_EMAILS`                   | your email — this account becomes the owner |

Optional:

| Variable              | Default | Effect                                              |
| --------------------- | ------- | --------------------------------------------------- |
| `SITE_URL`            | derived | Set once a custom domain is mapped                  |
| `GOOGLE_SIGN_IN`      | `false` | Show the Google button. Needs an OAuth client first |
| `GCP_BILLING_ACCOUNT` | unset   | Enables the budget alert                            |
| `BUDGET_ALERT_EMAILS` | unset   | Comma-separated addresses for that alert            |

### 3. Look before you leap

Actions → Deploy → Run workflow → **plan only**. This runs `terraform validate` and
`terraform plan` and stops. On a fresh project it should propose roughly forty resources
and destroy nothing.

### 4. Deploy

Push to the deploy branch, or run the workflow without `plan only`.

The first run takes about ten minutes, most of it waiting on Firestore to provision.

## What a deploy does

```
verify ─ typecheck, lint, unit tests
   │
deploy
   ├─ authenticate with a GitHub OIDC token (no keys)
   ├─ terraform init / fmt / validate
   ├─ terraform apply ─ infrastructure, service left on its current image
   ├─ reconcile the site URL against what Cloud Run assigned
   ├─ docker build ─ with the Firebase config and origin Terraform produced
   ├─ docker push  ─ Artifact Registry
   ├─ terraform apply ─ service moves to the new image, pinned by digest
   └─ smoke ─ the site answers 200 and carries its own CSP header
```

### Why two applies

Next inlines `NEXT_PUBLIC_*` into the browser bundle **at build time**. Those values — the
Firebase API key, the app ID, the origin — do not exist until Terraform has created the
Firebase web app and the service. So the infrastructure has to exist before the image can be
built, and the image has to exist before the service can point at it. The first apply passes
the image the service is already running, which makes it a no-op for the service itself.

On the very first run there is no image at all, so the service comes up on Google's `hello`
container for about two minutes before the second apply replaces it.

### Why the site URL is derived rather than read

The service's own environment and the bucket's CORS policy both need the origin, so reading
it off the service would make the service depend on itself. Terraform derives it instead —
`https://{service}-{project-number}.{region}.run.app` — and the workflow compares that
against the URL Cloud Run actually assigned. If they ever disagree, it re-applies with the
real one in the same run.

## Putting it on a real domain

The site runs on its `run.app` URL until `SITE_URL` names something else. Do this **before
sending a single real invitation**: an invitation lives in someone's inbox for weeks and is
opened the night before the party, so a link on a URL you later abandon is a dead link to a
real guest at a real event. It cannot be fixed after the fact.

1. **Verify the domain, by DNS.** Terraform has no API for this.

   `gcloud domains verify` offers an HTML file. Do not use it: the file has to be served
   from the domain being verified, and nothing serves that domain until the mapping exists,
   which needs the verification. Verify by TXT instead — it is the method that works before
   anything is live.

   [Search Console](https://search.google.com/search-console) → Add property → **Domain**
   (not "URL prefix") → add the `google-site-verification=…` TXT record it gives you on the
   apex, then verify.

2. **Add the deploy service account as a property owner.** This is the step that is easy to
   miss and fails confusingly. The mapping is created by CI, running as
   `marquee-deployer@…`, and Google checks that _that_ identity owns the verified property
   — verifying it as yourself is not enough. In Search Console: Settings → Users and
   permissions → Add user → the deployer's email → **Owner**.

   Confirm with `gcloud domains list-user-verified`.

3. **Set `SITE_URL`** to `https://marqueersvp.com` as a repository variable and deploy.
   Terraform creates the Cloud Run domain mapping and outputs the DNS records to add.

   Cloud Run's own mapping rather than a load balancer, deliberately: a global HTTPS load
   balancer carries roughly $18 a month in standing charges for capability this does not
   need. Mapping is free and manages its own certificate.

4. **Add the DNS records** it outputs at your registrar — usually four `A` and four `AAAA`
   records for the apex, or one `CNAME` for a subdomain. The certificate provisions within
   about fifteen minutes of the records resolving.

### On Cloudflare specifically

**Turn the proxy off** — the grey cloud, "DNS only", on every record Cloud Run gives you.
Proxied (orange) records stop Google provisioning the managed certificate, and the symptom
is a certificate error or a redirect loop rather than anything that names the cause.
Cloudflare's own TLS terminates at their edge, which is not what the mapping is checking.

**Pick one hostname and mean it.** Invitation links get pasted into text messages, so the
apex is the better canonical: `marqueersvp.com/i/ABCD1234` reads better than the same thing
with `www.` in front. Map the apex, and add a Cloudflare Redirect Rule sending
`www.marqueersvp.com/*` to `https://marqueersvp.com/$1`. Serving both without a redirect
splits every shared link across two origins and breaks sign-in on whichever one is not in
`authorized_domains`.

A `CNAME` pointing straight at the `run.app` hostname does not work, whichever host you
choose. Cloud Run routes by the domain mapping, so it answers such a request with a
certificate for the wrong name. The apex takes the four `A` and four `AAAA` records the
mapping outputs; a subdomain takes a `CNAME` to `ghs.googlehosted.com`.

Everything else follows from `SITE_URL` on the next deploy: the bucket's CORS origin, the
`authorized_domains` Firebase Auth will complete a sign-in link against, and the origin
baked into the invitation links in outgoing mail.

**Mind the OAuth client.** If Google sign-in is configured, add the new origin to the
client's authorised JavaScript origins, or the button breaks the moment the domain changes.

## Deliberately deferred

Both are wired end-to-end and switched off, so turning them on is a variable change and a
deploy, not a migration.

### Email — `email_driver = "outbox"`

Invitations are written to a Firestore `mailOutbox` collection instead of being sent. Every
part of the invite flow works; the messages just land somewhere only you can read.

To go live: create a Resend account, verify a **sending subdomain** (`mail.yourdomain.com`,
not the apex — a blocked apex domain takes your ordinary email down with it), then set
`RESEND_API_KEY` in Secret Manager and flip `email_driver` to `resend`.

### Payments — `billing_driver = "mock"`

`features.billing` is also `false`, so every event runs on the preview plan and nothing is
gated. The checkout endpoint refuses to run. Nobody can be charged, and no half-configured
Stripe key can take real money by accident.

To go live: create the Stripe account and two prices, add the four Stripe secrets, set
`billing_driver = "stripe"` and `FEATURE_BILLING=true`.

### Google sign-in — `google_sign_in = false`

Email-link sign-in is configured by Terraform and works immediately. Google sign-in needs an
OAuth client and a reviewed consent screen, which is console work no pipeline can do. Until
then the app offers the email link alone rather than a button that fails on the first click.

To enable: create an OAuth 2.0 Web client, add it to Firebase Auth → Sign-in method →
Google, then set the `GOOGLE_SIGN_IN` repository variable to `true` and redeploy.

## Costs

At zero traffic the stack costs **approximately nothing**: Cloud Run idles at zero
instances, Firestore and Cloud Scheduler stay inside their free tiers, and the only standing
charges are stored bytes and a few cents of Artifact Registry.

The lines that grow are storage and egress, which is why the app resizes images before
upload and serves derivatives rather than originals — see
[ARCHITECTURE.md](./ARCHITECTURE.md#media-is-resized-before-it-is-uploaded).

Guards already in place:

- `max_instances = 4` caps concurrent instances, so a traffic spike is a queue, not a bill.
- The bucket has a 90-day lifecycle rule behind the hourly sweep, so a bug in the sweep is a
  bounded cost rather than rent paid forever.
- Soft delete is **disabled** on the bucket. Its 7-day default retention bills for objects
  the app has deliberately deleted, which for an ephemeral media product is pure waste.
- Artifact Registry keeps the last ten images and deletes anything older than 30 days.
- Set `GCP_BILLING_ACCOUNT` and `BUDGET_ALERT_EMAILS` to get alerts at 50/90/100% of budget.

## Operating it

**Roll back.** Cloud Run keeps every revision. Send traffic to the previous one in the
console, or push a revert — a revert is better, because otherwise the next deploy silently
undoes the rollback.

**Read the sweep.** Cloud Scheduler → `marquee-cleanup` → the log of each run. If it stops
succeeding, expired media stops being deleted and the storage bill starts climbing.

**Secrets.** Generated by Terraform and marked `ignore_changes`, so an apply never rotates
them by accident. Rotating `JOIN_CODE_PEPPER` invalidates every outstanding join code, which
is a real thing to do and never an accidental one.

**Destroy.** `terraform destroy` will not take the database with it: Firestore is created
with delete protection on and an `ABANDON` deletion policy. Removing it is a deliberate,
console-confirmed act.

## Troubleshooting

| Symptom                                                    | Cause                                                                                                                                                                                           |
| ---------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Every photo and upload fails with a permission error       | The runtime account cannot sign V4 URLs. It needs `serviceAccountTokenCreator` **on itself** and `iamcredentials.googleapis.com` enabled — both are in Terraform, so check the apply succeeded. |
| `google_identity_platform_config` fails on the first apply | Identity Platform is still initialising on a brand-new project. Re-run the workflow.                                                                                                            |
| Sign-in link opens and immediately fails                   | The origin is not in `authorized_domains`. Check `site_url` reconciled correctly.                                                                                                               |
| Deploy fails on `terraform fmt -check`                     | Run `terraform fmt -recursive` in `infra/terraform` and commit.                                                                                                                                 |
| Uploads fail with a CORS error                             | The bucket's CORS origin is the previous `site_url`. Redeploy after setting `SITE_URL`.                                                                                                         |
| Smoke step gets a 404                                      | The derived origin was wrong and reconciliation did not catch it. Set `SITE_URL` explicitly to the URL in the Cloud Run console.                                                                |
